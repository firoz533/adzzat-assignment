Prompt
Recover the parameters of an epidemic that was interrupted by an intervention on an unknown day, and deliver the method as a reusable fitter.

`/app/data/cases.csv` holds 120 days of reported cases from a single outbreak. The counts are an under-reported, noisy view of the true daily infections. The outbreak follows an SEIR model whose transmission rate dropped once, from `beta1` to `beta2`, at an unknown time `t_switch`. The population `N` and incubation rate `sigma` are known and given in `/app/data/meta.json`. The recovery rate `gamma`, the reporting fraction `rho`, the initial number infected `I0`, both transmission rates and the switch time are unknown. The exact equations, the observation model and the output schema are specified in `/app/CONTRACT.md`.

Write `/app/submission/fit.py`. It must accept `--input`, `--output`, `--population` and `--sigma`, read the CSV, and write a JSON file containing point estimates for all six unknowns, a 95 percent confidence interval for each, and the fitted expected reported count for each of the 120 days. The script may import only numpy, scipy, pandas and the standard library. It must be deterministic: two runs on the same input must give the same estimates.

Verification runs your script on the supplied dataset and on a hidden dataset generated from the same model with a different population, incubation rate, parameter values and noise draw. Five criteria are checked on both datasets, each with the tolerances stated in the contract:

1. Pre-switch transmission rate, recovery rate and the fitted daily means.
2. The switch day and the post-switch transmission rate.
3. The reporting fraction and the initial number infected.
4. Interval calibration: every interval must contain the true value and must not exceed a stated width.
5. Efficiency: each run completes within 240 seconds on two CPU cores with 2 GiB of memory, and repeated runs agree.

The reward is 1 only when all five criteria pass on both datasets. Individual outcomes are recorded for diagnosis. No network access is available or needed. Only `/app/submission` is transferred to the verifier, which runs the script as an unprivileged user with a 300-second limit per invocation.
Prompt Quality
The objective (recover six named parameters with 95 percent intervals and fitted means, delivered as a CLI script at a fixed path with a fixed interface) is explicit; equations, observation model and output schema are in /app/CONTRACT.md inside the agent image; the five verified criteria are named with tolerances in the contract. Completing it requires exploring the data, writing and iterating on a numerical fitter, checking identifiability and runtime, so it is agentic, not single-shot.
Rubric Accuracy
Each criterion is a deterministic numeric comparison against the generating parameters or the noiseless mean, with explicit tolerances stated in the contract and encoded in tests/fixtures/*.json. Values were reproduced from the fixtures: visible t_switch 41.3, hidden 66.4, tolerances as listed. All weights are positive for desired behaviour. Tolerances were derived from the Fisher information and confirmed by an independent oracle across several noise seeds, so they are justified by the data rather than arbitrary.
Test Correctness
grade.py performs numeric comparisons with finite checks, bounded JSON reads, unprivileged execution and a timeout; no string matching. The reproducibility assertion (relative 1e-6 between two runs) is a real requirement stated in the prompt. The interval check requires containment and a width ceiling, so neither degenerate nor inflated intervals pass. One residual fragility: containment of the true value by a 95 percent interval is a probabilistic event on a fixed dataset; the fixture seeds were chosen so the maximum-likelihood estimate sits within 0.25 standard errors of the truth, which makes a correct method pass with margin, and this choice is documented in author/calibration.md.
Coverage & Balance
Every requirement in the prompt maps to one criterion: strong parameters and fit (1), switch (2), weak parameters (3), interval calibration (4), efficiency and determinism (5). The highest weights go to the identifiability-driven criteria (2 and 3), which are the hard core of the task. No requirement is graded twice.
Task Adequacy

The hidden dataset is intentionally absent and the prompt says so; a method that generalises is the point. No network is needed.
Prompt
Make the job pipeline in `/app/pipeline` correct when its workers are killed and restarted.

The pipeline takes jobs from a SQLite queue. For each job a worker computes a result, calls an external effect service, writes an output file, records an output row, adds the amount to the customer's running totals and marks the job done. Several workers run at once. Everything is right when no worker dies. When a worker is killed mid-job, jobs are stranded, effects are repeated or lost, and the totals drift away from the outputs.

The exact system, the runtime modules, the required behaviour and the delivery path are specified in `/app/CONTRACT.md`. The effect service lives outside the database and deduplicates only on the idempotency key it is given. The worker calls `chaos.point(name)` at seven fixed places; the harness uses those calls to kill a worker at a precise moment and then starts a replacement. The points must stay where they are and keep their meaning.

Change the pipeline so that, after any sequence of kills and restarts, once all workers have exited: every job is done exactly once with one output row; the effect service has delivered exactly one effect per job; every customer's totals equal the sum over that customer's outputs and the output files match the rows; a job held by a killed worker is finished within 15 seconds of the kill; and with no crashes the batch still completes within 30 seconds. A worker may only exit once every job is done.

Deliver the complete modified package at `/app/submission/pipeline`. You may change the schema, the claim logic, the transactions, the file handling and the module layout. You may not change the runtime modules; the verifier substitutes its own copies and runs your workers as an unprivileged user.

Verification runs one scenario with no crashes and fourteen scenarios that kill one worker at each instrumentation point on its first and on its third hit, restarting it each time. Five criteria are checked across those scenarios: completeness, exactly-once effects, consistent bookkeeping, prompt recovery, and clean throughput. Each criterion must hold in every scenario it covers. The reward is 1 only when all five pass; individual outcomes are kept for diagnosis. `/app/tools/run_scenario.py` reproduces any single scenario. No network access is available or needed.
Prompt Quality
The prompt states the system, the failure (workers killed mid-job), the five required behaviours with their numeric bounds, the constraint on instrumentation points, the delivery path and the verification scheme; /app/CONTRACT.md in the image gives the full specification and a reproduction tool. The work requires reading the pipeline, reproducing crashes with the harness, redesigning claim, effect, transaction and exit logic, and re-testing, which is multi-step.
Rubric Accuracy
Each criterion is an invariant on the final SQLite state, output directory and effect-service log after a scenario, evaluated by the harness; all are pass/fail with concrete bounds (15 s recovery, 60 s crash scenario, 30 s clean, 40 jobs). Values reproduced from tests/harness/harness.py constants. Weights are positive for desired behaviour. The invariants are interleaving-independent, so no arbitrary schedule is being selected.
Test Correctness
The grader verifies behaviour, not text: it runs 15 scenarios with the verifier's own chaos and effects modules shadowing the submission, checks the seven instrumentation points were executed, and asserts the invariants. Exit-code filtering (0 or 137) prevents a crashing-but-complete worker from passing silently. The timing bounds (15 s, 30 s, 60 s) are generous relative to the oracle (4 s recovery, 1.5 s clean), so they are not brittle on a two-core container. A residual limitation: the fencing-token requirement for a slow worker whose lease expired is only exercised when leases are very short; the scenario set does not force it, so a solution without fencing can pass. This is noted in author/calibration.md as a possible future scenario.
Coverage & Balance
Completeness, exactly-once effects, consistency, recovery and clean throughput each correspond to a distinct mechanism (lease reclaim and exit rule, stable idempotency key, single transaction, lease length, no regression). The heaviest weight is on exactly-once effects, which is the hardest part because the effect lives outside the database. Completeness 4 rather than 5 because the double-commit race described above is not forced by a scenario.
Task Adequacy
The agent has the full pipeline source, the runtime modules it must call, the contract, sqlite3 CLI and the same scenario harness the verifier uses, so any scenario can be reproduced locally. Standard library only; no network.
